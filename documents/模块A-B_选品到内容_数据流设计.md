## 0. 四条必须先纠正的判断（不改，后面全白做）

### 0.1 卖家精灵 API 你用不起，MCP 是唯一路径 —— 但用法必须改

官方定价（2026-07 口径，来源：open.sellersprite.com/pricing/api，以登录后页面为准）：

| 接口 | 单价 | 额度 |
|---|---|---|
| 选产品 | **¥3,999/月** | 2 万次 |
| 查竞品 | ¥2,999/月 | 2 万次 |
| ASIN 竞品数据 | ¥6,988/月 | 2 万次 |
| ASIN 详情 | ¥988/月 | 5 万次 |
| 产品类目 | ¥680/月 | 5 万次 |

API 按接口分别售卖，选品跑通至少需"选产品 + ASIN 详情" ≈ ¥4,987/月。个人不可行。

MCP 套餐：Basic ¥990/年 / 40 次每分 / 4000 次每月；Pro ¥1,990/年 / 60 次每分 / 10000 次；Max ¥2,990/年 / 80 次每分 / 15000 次。

**但用法必须改**：

| 错误用法 | 正确用法 |
|---|---|
| 把 MCP 挂给 LLM，让模型自己选工具 | **代码写死工具名与参数**，直调 `tools/call` |
| 每次调用过一遍 LLM 决策 | 0 次 LLM，纯 HTTP + JSON |
| 拿"AI 整理后的分析结果" | 拿原始 JSON，Pydantic 校验成强类型 |
| 无法算成本/重试/降级 | 超时/重试/限流/缓存/额度守卫全在客户端统一做 |

一句话：**把 MCP 当便宜的 HTTP 数据接口用，不当"给 AI 的工具"用。**

面试口径：MCP 是给 AI 客户端用的协议；我的数据获取是确定性工作流——给定品类和筛选条件，调哪个接口是固定的，不需要模型决策。所以我在代码层直连服务端，工具选择写死，只在 Agent 需要自主探索时才把工具交给 LLM。

`[待验证]` Python 官方 `mcp` SDK 的 streamable HTTP client 能否在非 AI 客户端环境下直连 `https://mcp.sellersprite.com/mcp`（header `secret-key`）。**这是整个数据层的前提，N2 第一件事，半天。**

`[待核实]` MCP 是否有**月付**套餐。公开可抓到的只有年费（990/1990/2990）。若只有年付，则"用到时再开通"的逻辑不成立（一次付清，全年可用），策略要改成"一次开通、全程用尽额度"。**开通前必须先问清**。

### 0.2 素材三档：竞品图只进提示词，不进像素

亚马逊官方原文（来源：gs.amazon.cn/zhishi/article-241002、sellercentral G200421970）：

> 主图必须是**实际商品的专业照片**（不得是图形、插图、实物模型）

你提的两条来源（竞品主图 / 自己拍摄）性质完全不同，**必须分开处理**：

| 档 | 素材 | 允许用来做什么 | 能否上架 |
|---|---|---|---|
| **S0 竞品图** | `asin_content_list` 返回的竞品主图 | **只做视觉方向参考**：构图、场景类型、色系、卖点图排布、拍摄角度 | ❌ **绝不** |
| **S1 供应商图** | 1688 / 供应商提供的产品图 | 抠图 → 白底 → 主图；附图基础 | ⚠️ 需图片授权，且产品必须与实际采购批次一致 |
| **S2 自拍图** | 你自己拍的产品 | 主图、场景图合成、视频素材 | ✅ 唯一完全合规来源 |

**硬规则：S0 只进提示词，不进像素。**

这条规则要用架构保证，不靠自觉：

```
prompt_builder(S0 分析结果, 产品信息) -> 视觉描述文本     # S0 只能到这里
image_pipeline(视觉描述文本, S1/S2 像素, 场景背景) -> 成品  # 像素入口只接受 S1/S2
```

图片生成函数的 `product_image` 参数**不允许**传 S0 目录路径，在代码层断言校验。这是"用架构保证合规"，面试可直接讲。

**为什么这条这么重要**：用竞品图生成自己的"产品图"，产出的是"看起来像竞品但又不是竞品"的东西——主图不合规、构成误导、且和实际收货商品不一致会引发投诉与退货。这比做不出图严重得多。

**你现在的实际约束**：选品阶段还没实物。所以分两段走——
- **选品/预售阶段**：只用 S0 做视觉方向 + 文案，产出的图标注"概念图，不可上架"
- **真上品阶段（N13 之后）**：有供应商图（S1）或自拍图（S2），才产出可上架主图

### 0.3 视频：AI 生成的是"氛围"，不是"产品"

| 镜头类型 | 做法 |
|---|---|
| 产品本体 | S1/S2 素材做 Ken Burns 推拉，或实拍短视频片段 |
| 场景氛围 | AI 视频生成可以，产品不入镜 |
| 卖点字幕/动效 | 代码渲染（PIL / FFmpeg drawtext） |
| 配音 | TTS（文本已知，时间轴按文本时长直接算） |
| 转场/节奏 | FFmpeg |

### 0.4 图片合规必须代码校验，不许 LLM 判断

亚马逊官方硬指标（来源：gs.amazon.cn/zhishi/article-241002）：

| 项 | 要求 | 代码可校验 |
|---|---|---|
| 背景 | 纯白 RGB(255,255,255) | ✅ 检测四角 + 边缘像素 |
| 产品占比 | ≥85% | ✅ 前景 mask 面积 / 总面积 |
| 最长边 | ≥1600px，≤10000px | ✅ 读 EXIF |
| 格式 | JPEG/TIFF/PNG，首选 JPEG | ✅ |
| 主图禁项 | 无 logo/水印/文字/边框/色块/道具/多角度/多颜色 | ⚠️ OCR 查文字 + 人工确认 |
| 主图必须实拍 | 不得是图形/插图/模型 | ❌ 代码判不了，靠 S0/S1/S2 流程约束 |

前四项 100% 代码判定，产出 `compliance_report.json`。

**五点描述硬约束**（同来源）：总长 <1000 字符、无 ®/™ 等特殊符号、无 HTML、无公司/促销/物流/邮箱信息、每条开头大写、结尾不加标点 —— 写成 6 条规则，生成后立即校验，不过就重写。

## 2. 重画后的数据流

```
【C 运营诊断】
 关键词方向 / 产品建议（类目·价格带·卖点）/ 差评痛点
        │
        ↓
┌───────────────────────────────────────────────────────┐
│  数据层：Snapshot-first（§2.5）                        │
│  MockSource / LiveSource(MCP) / SnapshotSource        │
└───────────────────────┬───────────────────────────────┘
                        ↓
① 选品筛（A）
   asin_list → 候选池 → asin_detail / prediction_sales
   → category_top_list / demand_report → asin_review_list
   输出：评分卡 + 3 个候选品
                        ↓ 选定 1 个
┌───────────────────────┴───────────────────────────────┐
│ ② 词库搭建（独立模块，见 §3）                          │
│ keyword_asin_list + related_list + aba_list + batch_info│
│ → 去重 → 打分 → 分层 → 打标                            │
│ 输出：分层词库 + 每层用途                              │
└───────────────────────┬───────────────────────────────┘
                        ↓
③ 文案（B-1）：词库 + 竞品五点（asin_content_list）+ 产品信息
   → 标题 / 五点 / A+ / ST + 埋词报告 → 6 条规则校验
                        ↓
④ 图片（B-2）
   S0 竞品图 → prompt_builder → 视觉描述（只进文字）
   S1/S2 像素 → 抠图 → 白底 → 合成场景 → compliance_report
                        ↓
⑤ 视频（B-3）
   分镜脚本 → S1/S2 素材 + AI 氛围镜头 → TTS → SRT → FFmpeg
```

**新增的一块是 ② 词库。** 原来"文案生成"是拿 ASIN 直接让 LLM 写，那是套壳；有词库后文案才有依据、可复现、可评测。

## 2.5 Snapshot-first 数据层（由"MCP 按需开通"倒逼产生）

你说"用到时再开通拿数据"——这个决策是对的，但它有一个必然的技术后果：

**代码不能时刻依赖 MCP 在线。** 开通期之外，开发、调试、评测、面试演示都必须能跑。所以数据访问必须全部经过一层抽象，底层可切换。

这是标准的 Repository 模式，也是这个项目里最容易讲出工程素养的地方。

### 2.5.1 三种实现，一个接口

```python
class DataSource(Protocol):
    def fetch(self, tool: str, params: dict) -> dict: ...
```

| 实现 | 何时用 | 数据来自 |
|---|---|---|
| `MockSource` | **开发期首选**，动手第一步 | `data/fixtures/` 手写最小样例 |
| `LiveSource` | MCP 开通期，只用来抓真数据和验字段 | 直连 `mcp.sellersprite.com/mcp` |
| `SnapshotSource` | 日常开发、评测、演示、断网 | `data/snapshots/<批次>/` |

由环境变量切换：`SS_SOURCE=mock | live | snapshot`

### 2.5.2 目录结构

```
data/
  fixtures/                        # 手写最小样例，无外部依赖
    asin_list.sample.json
    asin_detail.sample.json
  snapshots/
    2026-11-15/                    # 一批 = 一次开通期抓取
      manifest.json                # 抓取时间、工具、参数、行数、额度消耗
      drift_report.json            # 字段漂移（见 §2.6）
      raw/
        asin_list__a1b2c3d4.json   # 原始返回，原样保存不加工
      parsed/
        asin_list__a1b2c3d4.json   # Pydantic 校验后的规范化结构
```

**原始返回必须原样保存。** 因为 schema 会变、你的解析逻辑也会改；留了原文才能重放。丢了原文，快照就废了。

### 2.5.3 缓存键

```
key = sha256(f"{tool}:{json.dumps(params, sort_keys=True, ensure_ascii=False)}")
```

同一个键命中直接读本地，不消耗额度。这既是省钱，也是让评测可复现的唯一办法。

### 2.5.4 正确的推进顺序（这条决定你省多少额度）

1. **先写 `MockSource` + 全流程跑通** —— 用假数据把选品→词库→文案→图→视频整条链跑到底
2. **再开通 MCP，只做一件事：验字段** —— 对每个工具跑 1–3 次，比对真实返回和你 mock 的结构差异，改 Pydantic 模型
3. **集中抓一轮快照** —— 覆盖到你所有评测集和演示需要的 ASIN/类目/关键词
4. **关掉，后续全用快照**

**顺序反了就是烧额度。** 代码没写好就开通，等于花 990 买一堆看不懂的 JSON。

好处（面试可讲）：数据层快照化之后，评测可复现、不依赖外部服务可用性、断网也能演示、成本可预测。

## 2.6 两个必须有的守卫

### 额度守卫 `QuotaGuard`

- 每次 live 调用前记录，本地计数（`data/quota/2026-11.json`）
- 到套餐额度 80% 拒绝新调用并告警，不静默超限（超限返回 `ERROR_VISIT_MAX`）
- 主动查询：`GET https://api.sellersprite.com/v1/visits`（需 `secret-key` header，返回当月可用次数）

### 字段漂移检测

每次 live 抓取后，对比上次同工具的返回 key 集合，diff 出新增/缺失字段，写 `drift_report.json`。

**这是发现"卖家精灵悄悄改字段"的唯一办法。** 没有它，某天你的解析静默返回空值，你会以为是 LLM 的问题，查两天。

### 已知的坑（官方文档明说）

| 坑 | 应对 |
|---|---|
| 同一查询条件只支持 TOP 2K 数据（底层限制） | 按排名/BSR/搜索量/销量**分段**获取 |
| **每个模块首次请求需先请求 1 次初始化** | 每个模块第一次调用要特殊处理，失败不算真失败 |
| 并发限制 40 次/分钟（Basic） | 客户端全局限流器，不许并发打满 |
| 错误码 `ERROR_VISIT_MAX` / `ERROR_SECRET_KEY_OVERDUE` | 分别对应"额度耗尽"和"密钥过期"，错误分类要分开处理 |

## 3. 词库模块设计（新增，最关键的一块）

### 3.1 数据来源：光有 ABA 不够，四类缺一不可

你说的"根据 ABA 数据 + MCP 数据"方向对，但 ABA 只提供**官方搜索热度**一个维度。只用它会漏掉两类最重要的词：

| 类别 | 工具 | 提供什么 | 缺了会怎样 |
|---|---|---|---|
| **① 竞品流量词** | `keyword_asin_list` | 竞品靠哪些词拿流量（含命中 ASIN 明细） | 不知道真实流量入口，词库全是"想当然的词" |
| **② 扩展词** | `keyword_related_list` | 从种子词向外扩的长尾/衍生词 | 词库规模不够，长尾覆盖不到 |
| **③ 官方热度** | `keyword_aba_list` / `keyword_aba_trend` | 搜索量、点击份额、转化份额 | 不知道哪个词真有人搜（**你已提到**） |
| **④ 转化数据** | `keyword_batch_info` / `keyword_conversion_analysis` | 购买率、竞争度、PPC 竞价、ACOS、CVR | 分不出"有人搜但不买"的词，也判不了否词 |

**四类合并才是完整词库。** 只有 ①③ 就是"热门词表"，不是能埋的词库。

### 3.2 分层结构

| 层 | 判定规则 | 用在哪 |
|---|---|---|
| **核心词**（2–3 个） | ABA 点击份额 top10% 且相关性高 | 标题前 60 字符 |
| **属性词** | 含材质/尺寸/颜色/功能修饰 | 五点、Search Terms |
| **场景词/人群词** | 含 for/gift/indoor/outdoor 等 | 五点、A+ |
| **长尾词** | 搜索量中低 + 购买率 top30% + 竞争度低 | 后台 ST、广告手动 |
| **否定词** | 高点击 + CVR 低于类目中位数 | 广告否词 |

### 3.3 代码 / LLM 分工（决定可测性）

| 步骤 | 用什么 | 理由 |
|---|---|---|
| 去重、合并、拼写变体归并 | 代码 | 确定性 |
| 搜索量/购买率/竞争度打分排序 | 代码 | 纯数值 |
| 分层（按阈值切） | 代码 | 阈值可调、可复现 |
| **相关性判定**（这词跟我产品有关吗） | LLM + embedding 相似度 | 需要语义 |
| 属性/场景归类 | LLM（结构化输出） | 需要语义 |
| 否定词判定 | 规则 + LLM 双签 | 误杀代价高 |

**原则：数值算的归代码，语义判断的归 LLM。** 这样词库可复现、可评测；LLM 只影响"哪些词进来"，不影响"怎么排序"。

### 3.4 评测指标

| 指标 | 怎么算 | 目标 |
|---|---|---|
| 词库覆盖率 | 竞品 Top10 流量词中有多少进了词库 | ≥85% |
| 埋词率 | 核心词 100% 出现在标题；属性词覆盖五点 | ≥80% |
| 相关性准确率 | 人工抽检 50 词判"该不该进库" | ≥90% |
| 否定词误杀率 | 被标否定的词里其实相关的比例 | ≤5% |
| 词库稳定性 | 同输入跑两次，Jaccard 相似度 | ≥0.95 |
