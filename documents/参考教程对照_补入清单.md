## 一、判定口径

每章只判四类，不做"好/不好"的评价：

| 判定 | 含义 | 处置 |
|---|---|---|
| **已有** | 我计划里已有，且深度够 | 不读，浪费时间 |
| **补入** | 我计划里缺，或只有一句话，而项目要用 | 写进技能表，给够用线 |
| **降级参考** | 我计划里有，但教程讲得更细 | 卡住时查对应节，不通读 |
| **不补** | 与项目无关，或已明确砍掉 | 写清理由，防止以后反复动摇 |

**核心原则不变：加深不加宽。** 补入只补"现有模块内部缺的那一层"，不新增模块。

## 三、补入项（10 条，逐条给够用线）

每条都写明：归属哪个模块、为什么需要、学到哪停、验收怎么测、工时。

### 1. 方案选型四问（认知层，0.5 天）

**归属**：全局判断，用在每次"这里该不该上 Agent / 要不要 RAG"的决策点。

| 现象 | 优先方案 |
|---|---|
| 模型没看到资料（不知道我的 SOP、类目知识） | RAG |
| 模型行为不稳（格式飘、标签不稳、JSON 常错） | 先改 Prompt，必要时微调 |
| 模型不懂领域语言（拿到资料也读不懂） | 续训 + RAG |
| 任务需要多步执行（查、调、校验、写） | 工作流；流程开放才用 Agent |

**够用线**：能对着自己项目的四个模块，各说一句"我为什么选这个形态，不选另一个"。
**验收（4 级）**：口述 90 秒——"图文为什么不是 Agent"，答不出 RAG vs 工作流的边界就算没过。

### 2. 检索增强三件套（1 天）

**归属**：D 知识库 / M5 运营诊断。

| 手段 | 解决什么 | 在我的项目里对应 |
|---|---|---|
| metadata filter | 只在某业务范围内找 | 只检索"广告"章节 / 只检索某类目 SOP |
| hybrid（稠密 + 稀疏/BM25） | 既看语义，又不丢关键词命中 | 型号、专有名词、错误码必须精确命中 |
| rerank | 召回对了但排序不稳 | 检索命中率@5 从 60% 拉到 80% 的关键 |

**够用线**：知道三者的先后顺序（先 filter 缩范围 → 混合召回 → rerank 重排），并能解释"为什么 rerank 不重新全库搜索"。
**验收（3 级）**：在自己的语料上跑一组对比——纯向量 vs 加 rerank，命中率@5 有数。

### 3. 切分策略与参数（0.5 天）

**归属**：D 知识库。教程 19 章 §2.3。

- 默认用 `RecursiveCharacterTextSplitter`：优先按段落、句子切，太长再往下切
- `chunk_size` 太大→相关信息被淹没；太小→语义被切碎
- `chunk_overlap` 常取块大小的 **10%–20%**，防止一句话被拦腰截断
- 我的语料是 Markdown（卖家大学文档），优先用 `MarkdownHeaderTextSplitter` 按标题切，再把父标题拼进块前缀

**够用线**：能说清"为什么长上下文模型也不能直接塞整篇文档"（无关信息稀释关键内容）。
**验收（2 级）**：同一份文档用 2 组参数切，看检索结果差异。

### 4. 容器数据边界（0.5 天）

**归属**：M6 生产化。教程 8 章 §4。

| 概念 | 要点 |
|---|---|
| named volume vs bind mount | 左边是名字=volume（引擎管理），左边是路径=bind（宿主机目录） |
| `down` vs `down -v` | 后者删 volume，**数据没了** |
| 判断数据在哪 | `docker inspect <容器> --format '{{json .Mounts}}'`，不靠感觉 |
| 排障顺序 | `compose ps` → `logs` → `inspect Mounts` → 进容器 |

**够用线**：能说出自己的 PG / Redis / Chroma 三个服务的数据分别挂在哪，以及哪条命令会删掉它们。
**验收（4 级）**：说清"为什么 `compose down` 通常不丢数据，但有前提"。

### 5. 结构化输出选型（0.5 天）

**归属**：所有要 LLM 出结构化结果的环节。教程 14 章 §8.2。

| 需求 | 方案 |
|---|---|
| 自由文本回复、摘要 | `StrOutputParser` |
| 抽几个简单字段 | `JsonOutputParser` |
| 接口返回固定字段 | `with_structured_output(TypedDict)` |
| 写库、写业务系统 | `with_structured_output(Pydantic)` |
| 与外部系统对齐协议 | JSON Schema |

**必须记住的三个误区**（教程 14 章 §9）：
1. 能解析成 JSON ≠ 数据正确（格式对、内容错照样过）
2. `Annotated` 只是描述，**不自带校验**
3. 输出解析器不能代替 Prompt 设计

**够用线**：给"选品评分卡"这个输出选一种方案，并说出为什么不用另一种。

### 6. Agent Middleware 与人类审核（1 天，含在 M1 内）

**归属**：M1 选品 Agent。教程 21 章 §4.8。

Middleware 是给 Agent 加**运行边界**的抓手，四类用途：

- 动态提示词（按用户/场景换 system prompt）
- **工具调用守护**：高风险工具执行前查参数、权限、业务规则
- **人类审核**：删除、支付、发布、批量修改，不许静默执行
- 日志与监控：记录决策、工具参数、异常、耗时

**和我已有设计的关系**：我的"工具权限分级 read/write/danger"是策略，middleware 是**落点**。没有落点，权限分级只是一张表。

**够用线**：能说清"发布类工具在 middleware 里怎么拦"。
**验收（4 级）**：说清为什么护栏要放在 middleware 而不是写在 Prompt 里。

### 7. State 设计与 Reducer（1 天）

**归属**：M1 选品 Agent。教程 23 章 §2–3。

| 字段语义 | Reducer |
|---|---|
| 只关心最新值（当前路由、最终结论） | 默认覆盖 |
| 消息历史、Agent 轨迹 | `add_messages` |
| 候选列表、文档片段、标签 | `operator.add` 或自定义去重 |
| 计数、分数、token 累计 | `operator.add` |
| 按 ID 合并、保留最高优先级 | 自定义 Reducer |

**两条实践铁律**：
- 并行分支写**同一个字符串字段**时别用 `operator.add`（拼接依赖写入顺序），改成"先收集列表，再由汇总节点统一排序拼接"
- State 字段不要无限膨胀，临时中间变量不必留在全局 State

**够用线**：给自己的选品 State 画一张字段表，每个字段标一个 Reducer 和理由。
**验收（4 级）**：说清"状态 bug 大多不是节点逻辑错，是合并规则没设计清楚"。

### 8. Send / Command / Runtime（1 天）

**归属**：M1 选品 Agent。教程 24 章 §3。

| 机制 | 解决什么 | 我的场景 |
|---|---|---|
| `Send` | 运行时才知道要开多少条并行分支，每条带不同状态 | **一批 ASIN 并行评分**（Map-Reduce） |
| `Command` | 节点内既更新状态又跳转 | 路由后直接进对应子流程 |
| `Runtime` context | 配置与状态分开 | 模型名、预算、开关不该混进 State |

**注意**：并行分支写回同一字段要配好 Reducer，否则结果汇总不了。

**够用线**：能把"给 20 个 ASIN 并行打分再汇总"这个需求用 `Send` + Reducer 画出来。
**验收（3 级）**：不看文档写出一个 Send 的最小例子。

### 9. stream_mode / Store / 子图（1.5 天）

**归属**：M1 + M5。教程 25 章。

| 能力 | 要点 |
|---|---|
| `stream_mode` | `values` 全量快照 / `updates` 增量 / `messages` token / `custom` 自定义 / `debug`；可传列表同时拿多种 |
| Store vs Checkpointer | Checkpointer 存**线程内**状态；Store 存**跨会话**长期信息（类目偏好、历史选品结论） |
| interrupt / HITL | 中断后恢复**节点会重新执行**，所以恢复逻辑要幂等 |
| 子图 | "单个 ASIN 调研"做成子图，主图只负责调度 |
| time-travel | 回到某个 checkpoints 重跑，调 Prompt 时很好用 |

**和我已有设计的关系**：SSE 往前端推什么，本质就是选哪个 `stream_mode`。这个对应关系现在是空白。
**够用线**：能说清"前端要显示'正在查第 3 个 ASIN'，该用哪个 mode"。

### 10. MCP 只读架构（2 小时）

**归属**：数据层。教程 20 章 §3、§5。

只取三样：
- 三角色：host / client / server
- 两类传输：STDIO（本地进程）vs HTTP（远程服务）
- 两个方法：`tools/list` 拿工具清单与 schema，`tools/call` 带参数调用

**为什么只读架构**：卖家精灵 MCP 我当**便宜 HTTP 接口**用（写死工具名、拿原始 JSON 过 Pydantic），不交给 LLM 选工具。知道协议长什么样，是为了排错和写对请求，不是为了把它挂给 Agent。

上游是活跃仓库（最后提交 2026-11-06），会继续更新。追踪规则：

1. **每次开工前**先 `git -C E:\ai-project\ai-agents-from-zero pull --ff-only`，看有没有新章节或章节改写
2. **每月核对一次** `docs/reference-tracking.md` 里的章节状态表，把已读的划掉、新增的补进去
3. **只在两种情况下重读**：① 我要做的那一步，对应章节被改写了；② 出现了我完全没有的新主题（如新的编排范式）

## 八、三条容易走偏的地方（教程与我的计划相反的点）

| 教程怎么说 | 我怎么做 | 为什么 |
|---|---|---|
| 把 MCP 通过 `McpClientAgent` 交给 Agent 自己选工具（20 章 §4.3、21 章 §5.4） | 写死工具名，直接 `tools/call`，拿原始 JSON 过 Pydantic | 数据获取是确定性工作流，不需要模型决策；让模型选工具会引入不确定性和额度浪费 |
| 用多智能体 + 子智能体做深度研搜 | 单 Agent + 三个确定性工作流 | 多智能体会让系统难测、成本不可预测；我的场景没有"开放任务"特征 |
| 先搭平台（Dify/Coze）再写代码 | 先写代码，Dify 只保留 2 个工作流做对照 | 平台会掩盖工程细节；我要的是能讲清每一层 |
